rag-multihop.mjs 代码分析报告

该脚本实现了“路由 + 多跳拆解 + 循环检索 + 动态规划 + 最终生成”的增强版 RAG，适合处理链式推理问题。

1) 整体流程（多跳 RAG）

START
→
route_question
→
simple?
→
direct_answer
→
END
route_question
→
decompose_question
→
retrieve
→
plan_next_step
→
retrieve / generate
→
END

与普通 RAG 不同点：复杂问题先拆为子问题序列，再分轮检索，并在每轮后由规划器判断“继续检索还是生成答案”。

2) 状态设计（GraphState）

基础输入

  • question：原始用户问题。
  • k：每轮检索 top-k。

路由相关

  • strategy：simple / complex。
  • routeReason：路由原因文本。

多跳相关

  • subQuestions：有序子问题列表。
  • nextSubIdx：下一轮检索子问题下标。
  • currentQuery：本轮实际检索 query。

循环控制

  • retrievalCount：已检索轮数。
  • maxRetrievals：最大检索轮数。
  • plannedNext：规划器决策 retrieve/generate。

结果相关

  • documents：累计去重后的文档池。
  • generation：最终回答。

4) 这份实现的优点

多跳拆解 循环检索 结构化决策 轮数上限兜底
  • 比单轮 RAG 更适合处理“人物关系链、因果链、跨章节事实”问题。
  • 有累计文档池与去重逻辑，证据覆盖更广。
  • 规划节点能在“证据够了”时提前结束，避免无意义检索。

5) 缺点 / 风险点

代码正确性风险

  • 当前代码片段中出现 newMap、returnArray、thrownewError 这类写法，若源码一致会直接运行失败。
  • 建议优先做语法与静态检查，先保证可运行。

路由与规划误判

  • 路由误判可能导致该检索的问题走直答，事实性下降。
  • 规划误判可能过早生成，造成证据不足。

性能与成本

  • 每轮都调用 LLM（拆解/规划/生成），复杂问题成本明显上升。
  • Milvus 在启动阶段就连接，simple 分支也承担初始化开销。

召回质量上限

  • 目前仅向量检索，无 rerank、无混合检索、无 metadata 精细过滤。
  • 多跳依赖拆解质量，若子问题质量差会放大误差。

可配置性不足

  • question、k、maxRetrievals、Milvus 地址等写死在代码里。
  • 建议支持 CLI 参数和环境变量，便于不同场景复用。

缺少自动化评估

  • 没有多跳问答基准集与回归测试，难以量化改动收益。
  • 建议建立“命中率/答案正确率/平均轮次/平均耗时”指标。

6) 建议的优化优先级

  1. 先修复潜在语法错误并加最小单测，保证流程可跑可回归。
  2. 改为 complex 分支才初始化 Milvus，降低 simple 路径延迟。
  3. 引入 rerank 与 metadata 过滤，提高每轮检索命中质量。
  4. 给路由/规划增加置信度与回退策略（低置信度时追加检索）。
