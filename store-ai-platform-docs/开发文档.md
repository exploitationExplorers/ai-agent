## 1. 产品定位与范围

### 1.1 一句话定位

面向**餐饮、服装两类实体小店**的一体化 SaaS：先用**收银和门店经营**功能留住店主、积累每天的经营数据；再由 **AI Agent** 读取这些数据，每天自动出选题、写口播脚本；接着用**店主的数字人分身**把脚本渲染成竖屏短视频，**一键发布到抖音 / 视频号**；视频带来的咨询线索**回流进系统私域**。拓客渠道靠**多级代理**。

### 1.2 核心业务闭环

```
收银/库存产生数据 → Agent 读数据、定选题、写脚本 → 数字人渲染视频 → 发布到抖音/视频号
      ↑                                                                    ↓
      └──────── 线索回流 → 客户档案 → 到店核销 / 会员消费 ←────────── 用户咨询
```

### 1.3 模块清单

| 编号 | 模块 | 端 | 优先级 |
|---|---|---|---|
| M1 | 门店经营（收银、聚合收款、商品库存、会员、报表、预警 + 餐饮/服装行业包） | App、小程序、Web 后台 | P0 |
| M2 | AI 智能 Agent（数据洞察、选题、脚本、话术、营销方案） | App、小程序、Web 后台 | P0（差异化卖点） |
| M3 | 数字人克隆（形象 + 声音克隆，9:16 视频渲染） | App、小程序 | P0 |
| M4 | 短视频分发 + 线索回流 | App、Web 后台 | P1 |
| M5 | 代理管理后台（分级、归属、佣金、结算、控价） | Web 后台 | P0（销售渠道需要，建议和 M1 并行开发） |
| M0 | 平台底座（多租户、账号权限、计费订阅、消息通知、文件存储、审计） | 全端 | P0 |

### 2.2 关键架构决策（ADR 摘要）

| # | 决策 | 理由 |
|---|---|---|
| ADR-1 | 后端先做 **Go 模块化单体**，不一开始就上微服务 | 团队规模小、领域边界还在变。模块之间只通过接口和事件通信，以后可以平滑拆分 |
| ADR-2 | 用 **Protobuf + Connect-RPC(buf)** 统一定义接口，自动生成 Go 服务端和 TS 客户端 | 前端人多，类型安全的客户端能减少联调；同时兼容 HTTP/JSON，小程序可以直接调用 |
| ADR-3 | **Agent 用 Go 实现（CloudWeGo Eino + Eino ADK）** | 和后端同语言，可以直接复用领域服务和事务；Eino 是字节开源的，和火山引擎/豆包生态对接顺畅 |
| ADR-4 | 数据读取统一走 **MCP Server** 暴露的只读工具 | Agent 不直接写 SQL，权限、租户隔离、审计都能收在一处；以后接入其他 Agent（比如店主在 App 里对话）也能复用 |
| ADR-5 | 长流程（生成视频、发布、结算）统一用 **Temporal** 编排 | 支持重试、补偿、人工确认节点、定时调度，而且 Temporal 的 Go SDK 是一等公民 |
| ADR-6 | **数字人先接 API，后期再自建 GPU 推理** | 前期先验证市场；月渲染量过万条再评估自建，可以省下 60%+ 成本 |
| ADR-7 | 视频后期合成用 **Remotion（React 写视频）** | 前端团队能直接写字幕、贴片、门店信息模板，和 Web 组件复用同一套设计体系 |
| ADR-8 | 聚合收款**接入持牌支付机构或服务商模式**，平台不经手资金 | 规避"二清"违规；代理佣金走分账或灵活用工平台 |
| ADR-9 | 多租户用 **PostgreSQL 行级安全(RLS) + tenant_id** | 一套库支撑海量小商户，隔离由数据库兜底，就算应用层漏写条件也不会串数据 |

## 4. Agent 框架与 AI 方案

### 4.1 框架选型结论

| 候选 | 语言 | 结论 |
|---|---|---|
| **CloudWeGo Eino + Eino ADK** | Go | ✅ **主选**。组件化（ChatModel、Tool、Retriever、Graph），ADK 提供 ChatModelAgent、Sequential/Parallel/Loop、Plan-Execute、Supervisor 多 Agent、中断恢复（Human-in-the-loop）；自带 MCP 工具适配和 Langfuse/CozeLoop 回调 |
| LangGraph.js / Mastra | TS | 🔶 备选。如果前端同学主导"店主 App 里的对话式助手"，可以用 TS 写一个 BFF Agent，通过 MCP 复用同一批 Go 工具 |
| Google ADK Go / OpenAI Agents SDK | Go / Py | ❌ 不选。国内模型生态适配和中文社区都不如 Eino |
| Dify / Coze 等低代码平台 | — | ❌ 核心链路不选（难以版本化、测试，也不好做多租户深度集成）；运营同学可以拿来做原型验证 |

**协议层**：
- **MCP（Model Context Protocol）**：用官方 `modelcontextprotocol/go-sdk` 实现「门店数据 MCP Server」，Agent 通过 MCP 调用只读工具。
- **AG-UI 协议**（可选）：App/Web 端的对话式 Agent 用 AG-UI 做流式事件（工具调用进度、中间状态、人工确认卡片），前端用 CopilotKit 或自研组件渲染。

### 4.2 模型选型（多模型路由）

| 任务 | 推荐模型（按优先级） | 说明 |
|---|---|---|
| 选题决策、营销方案（需要推理） | 豆包 Seed 系列 / DeepSeek 最新版 / Qwen 最新旗舰 | 用结构化输出（JSON Schema） |
| 口播脚本、话术（需要创意 + 口语化） | 豆包 / Qwen / Kimi | 用少样本（few-shot）爆款模板 |
| 违规词、广告法审核（量大、成本敏感） | 小模型（Qwen 小尺寸 / 豆包 lite）+ 规则词库 | 先规则再模型，双保险 |
| Embedding | 豆包 Embedding / BGE-M3 / Qwen3-Embedding | 模板库检索 |
| ASR（字幕时间轴） | 火山引擎 ASR / **FunASR / SenseVoice**（自建） | 需要字级时间戳 |

> 通过 **AI 网关**（Higress AI 插件或自研 `llm-router`）统一管理：多家厂商自动切换、Token 计量（按租户计费）、缓存、限流、Prompt 版本。
> **合规要求**：只能调用**已完成生成式 AI 备案**的模型（国内主流厂商都有）。

### 4.3 Agent 整体设计：「每日营销官」

```
         Temporal 定时 (每天 07:30 按租户分批)  或  店主手动触发 / 事件触发(stock.low)
                                   │
                ┌──────────────────▼──────────────────┐
  Step1         │  DataCollector（确定性代码，非 LLM）    │  ← MCP 工具读取当日/昨日数据
                │  生成 StoreDailySnapshot(JSON)       │
                └──────────────────┬──────────────────┘
                ┌──────────────────▼──────────────────┐
  Step2         │  SignalDetector（规则引擎，非 LLM）    │  库存≤阈值 / 爆款TopN / 滞销N天
                │  输出 Signal[]（带分数与证据）          │  新品上新 / 营业额异动 / 节气节日
                └──────────────────┬──────────────────┘
                ┌──────────────────▼──────────────────┐
  Step3         │  TopicPlanner Agent（LLM）            │  结合行业、季节、门店风格、
                │  选出 1~3 个选题 + 营销目标            │  历史视频效果，输出结构化选题
                └──────────────────┬──────────────────┘
                ┌──────────────────▼──────────────────┐
  Step4         │  ScriptWriter Agent（LLM + RAG）      │  检索餐饮/服装爆款模板库
                │  生成口播脚本（钩子-卖点-促单-引导）      │  输出分镜/字幕/时长/标签
                └──────────────────┬──────────────────┘
                ┌──────────────────▼──────────────────┐
  Step5         │  Reviewer Agent（规则 + LLM）          │  广告法极限词、平台违规词、
                │  不通过 → 带修改意见回到 Step4（≤2 轮）  │  价格/库存事实核对（防幻觉）
                └──────────────────┬──────────────────┘
                ┌──────────────────▼──────────────────┐
  Step6         │  Human-in-the-loop：推送给店主确认      │  可编辑、可换一版、可一键生成视频
                └──────────────────┬──────────────────┘
                                   ▼
                        进入 M3 数字人渲染流水线
```

**设计要点**

1. **"数据的事交给代码，创意的事交给模型"**：Step1、Step2 是确定性代码，保证数字准确（比如"仅剩 3 件"必须来自数据库）。LLM 只负责选题和写作。
2. **事实锚定**：脚本里出现的价格、库存、折扣、门店地址，都必须引用 Snapshot 里的字段；Reviewer 逐项核对，防止幻觉。
3. **Eino 实现方式**：外层用 Eino `compose.Graph` 编排确定性节点和 Agent 节点；Step3 到 Step5 用 ADK 的 `SequentialAgent` + `LoopAgent`（写作↔审核循环）；Step6 用 ADK 的中断/恢复（Interrupt/Resume）配合 Temporal Signal。
4. **记忆**：门店画像（风格、人设、禁用词、常用优惠）存在 `store_profile`；视频历史效果（播放、点赞、线索数）写回 `content_performance`，作为 TopicPlanner 的参考信号，形成"越用越懂你"的闭环。
5. **可评测**：建立 200+ 条黄金样本集（快照 → 期望选题/脚本），每次改 Prompt 或换模型都在 Langfuse/CozeLoop 上跑回归评测。

### 4.4 MCP 工具清单（门店数据 MCP Server，只读）

| 工具名 | 入参 | 返回 |
|---|---|---|
| `get_daily_revenue` | store_id, date | 营业额、订单数、客单价、同比/环比 |
| `get_top_products` | store_id, date_range, limit | 爆款 TopN（销量、销售额、毛利） |
| `get_low_stock_items` | store_id | 低于预警值的 SKU（服装含颜色/尺码维度） |
| `get_new_arrivals` | store_id, days | 新品列表（含主图） |
| `get_slow_moving_items` | store_id, days_without_sale | 滞销货品、库龄、积压金额 |
| `get_member_stats` | store_id, date_range | 新增会员、复购率、沉睡会员数 |
| `get_store_profile` | store_id | 门店名、地址、电话、营业时间、人设、风格 |
| `get_content_performance` | store_id, days | 历史视频的效果数据 |
| `search_script_templates` | industry, scene, keywords | 爆款模板（向量 + 标签检索） |
| `get_calendar_context` | date, city | 节日、节气、天气（用于选题） |

> 所有工具都强制从上下文注入 `tenant_id`，**模型不能传租户参数**；工具层再加一层 PG RLS 兜底。

### 4.5 基础 AI 功能（店主主动使用）

| 功能 | 实现 |
|---|---|
| 话术生成（朋友圈、社群、私信回复、点评回复） | 单 Agent + 场景模板 |

### 4.6 文案模板库设计

- 结构：`industry`（餐饮/服装）× `scene`（清仓、爆款、新品、低库存、节日、探店、上新、会员日……）× `hook_type`（悬念、痛点、反差、福利、紧迫感）

### 5.3 M3 数字人克隆

#### 5.3.1 流程

```
店主上传 15~30s 正脸口播视频
   → 质检（时长、分辨率≥1080p、人脸检测、单人、光线、正脸角度、背景噪音）
   → 签署《肖像及声音授权书》（电子签 + 活体/实名比对，合规必须）
   → 形象克隆（数字人厂商 API 训练 / 自建）
   → 声音克隆（厂商声音复刻 API / 自建）
   → 生成试听样片 → 店主确认 → 形象可用
```

#### 5.3.2 渲染流水线（Temporal Workflow：`RenderVideoWorkflow`）

```
脚本 → TTS(克隆声音，得到音频 + 字级时间戳)
     → 数字人口型驱动(形象 + 音频 → 9:16 口播视频, 1080x1920)
     → Remotion 后期合成：
         · 自动字幕（关键词高亮、逐字动画）
         · BGM（按情绪匹配版权曲库，自动压低人声段音量 ducking）
         · 门店定位文字 / 地址 / 电话 贴片、片尾二维码
         · 商品图画中画（可选）
         · AI 生成内容标识（合规强制，显式水印 + 元数据隐式标识）
     → FFmpeg 转码（H.264/H.265，抖音推荐码率）→ 封面生成
     → 上传 OSS → 通知店主预览
```

#### 5.3.3 方案选型

| 阶段 | 形象 / 口型 | 声音 | 说明 |
|---|---|---|---|
| **MVP（推荐）** | 火山引擎数字人 / 即梦 OmniHuman 系列 API，或硅基智能、腾讯智影等商用 API（按效果、价格 PK 选一家主用 + 一家备用） | 火山引擎声音复刻 / MiniMax 声音克隆 / 阿里 CosyVoice API | 最快上线，按分钟计费 |
| **规模化（月渲染 >1 万条）** | 自建 GPU：**LatentSync / MuseTalk / EchoMimic / HunyuanVideo-Avatar** 等开源口型驱动模型（选型时按最新 SOTA 实测） | 自建 **CosyVoice / Fish-Speech / IndexTTS** 等开源 TTS | GPU 推理服务用 Python（FastAPI + Ray Serve / Triton），通过队列与 Go 解耦 |

### 5.5 M5 代理管理后台

| 功能 | 规则设计 |
|---|---|
| 代理分级 | 平台 → 省级 → 市级 → 区县 → 业务员（层级可配置，建议**不超过 3 级分佣**，避免触碰传销红线） |
| 客户归属 | **报备制**：代理先报备商户（手机号 / 营业执照），保护期（如 30 天）内签约就归属该代理；签约后永久归属，支持平台仲裁转移；每次归属变更都要留痕 |
| 佣金规则 | 首购佣金比例 + 续费佣金比例（续费持续拿佣金）+ 级差（上级拿差价）；规则**版本化**，订单按下单时的规则快照计算 |
| 结算周期 | **T+15**：订单支付后进入"冻结期"（覆盖退款期）→ 每 15 天一个结算批次 → 生成结算单 → 代理确认 → 打款 |
| 打款方式 | ①支付机构**分账**；②**灵活用工 / 税筹平台**（个人代理要代扣个税，并开具发票）；③企业代理对公打款 + 开票 |
| 乱价管控 | **所有订单统一通过平台收银台下单付款**，代理不能私自收款；平台定建议价，代理可以在授权价格区间内设置折扣码；低于底价直接拦截；异常订单监控（同一执照多次低价开户、频繁退款等）；违规罚则写进代理协议 |
| 代理自己的数据 | 名下商户、续费到期提醒、业绩、团队、佣金明细、推广二维码 / 邀请链接 |
| 平台运营后台 | 代理审核、层级调整、规则配置、结算审核、对账、黑名单 |

**佣金计算示意**

```
商户年费 3980 元，由区代 C 签约；C 的上级是市代 B，B 的上级是省代 A
各级的"总佣金比例"：区代 35%，市代 45%，省代 50%

级差制（推荐）：每一级拿"自己的比例 − 下级的比例"
  C = 3980 × 35%          = 1393.00 元
  B = 3980 × (45% − 35%)  =  398.00 元
  A = 3980 × (50% − 45%)  =  199.00 元
  平台总共让利 50%（1990 元），和成交链条上有几级无关，成本可控

续费：按 renew_rate（比如首购比例的 60%）用同样的级差规则计算，只要商户续费就持续产生佣金
→ 所有计算在 commission 模块里用"规则引擎 + 规则快照"实现，金额一律用整数"分"存储
```

> 具体分佣模型（直接比例 or 级差）需要客户确认，见第 14.3 节待确认问题。

## 7. 接口与工程规范

### 7.1 API 规范

- 接口定义放在 `proto/`，按领域分包：`proto/store/v1/inventory.proto`
- 统一用 **Connect 协议**；Web / App 用 `@connectrpc/connect-web`；小程序通过自定义 transport（基于 `Taro.request`）调用 Connect 的 JSON 模式
- 错误码：Connect 标准 Code + `ErrorDetail{reason, metadata}`，前端统一处理
- 分页：cursor 分页
- 幂等：写接口支持 `Idempotency-Key`（收银、支付、发布必须支持）
- 鉴权：短期 JWT（15 分钟）+ Refresh Token；请求上下文带 `tenant_id` / `store_id` / `role`
- `buf lint` + `buf breaking` 放进 CI，防止接口出现不兼容变更

### 7.2 Go 代码规范（给 AI 的硬约束）

- 分层：`handler (connect) → service (业务) → repo (sqlc)`；跨模块只能调用对方 `service` 的接口，**不能跨模块直接访问对方的表**
- 所有函数第一个参数是 `ctx context.Context`；租户信息从 ctx 里取
- 错误用 `fmt.Errorf("...: %w", err)` 包装；不要吞错误
- 金额只用 `int64`（分）；库存扣减用 `UPDATE ... SET qty = qty - $1 WHERE qty >= $1` 或乐观锁
- 每个 service 方法都要有单元测试；repo 用 testcontainers 跑集成测试
- `golangci-lint` 零告警

### 7.3 前端规范

- TypeScript `strict`；禁止 `any`
- 服务端数据只通过 TanStack Query 管理；API 客户端只用生成的 `api-client` 包
- 组件放 `packages/ui`，业务页面放 `apps/*`；行业差异组件用 `industry/fnb`、`industry/apparel` 目录隔离
- Vitest + Testing Library；关键流程（收银、点餐、发布）用 **Playwright** 做 E2E
- Biome 或 ESLint + Prettier

## 10. 让 AI 自动化开发的工作方式

### 10.1 核心思路：**规格驱动开发（Spec-Driven Development）**

```
人：写/确认 Spec（需求 + 验收标准）
 → AI：根据 Spec 先改 proto 和数据库迁移 → 生成代码 → 实现 service → 写测试 → 实现前端
 → CI：lint + 测试 + buf breaking + E2E
 → 人：Code Review + 验收
```

AI 最怕"模糊需求 + 没有约束"。所以要准备好下面 4 类文件：

| 文件 | 作用 |
|---|---|
| `AGENTS.md`（根目录） | 项目总纲：技术栈、目录约定、命令、禁止事项（Cursor、Claude Code、Codex 都会读） |
| `.cursor/rules/*.mdc` | 分目录规则：`backend.mdc`、`frontend.mdc`、`mini.mdc`、`proto.mdc`、`ai-agent.mdc` |
| `docs/specs/<模块>-<功能>.md` | 每个功能一份 Spec（模板见 10.3） |
| `docs/adr/*.md` | 重大技术决策，防止 AI"自作主张"换方案 |

### 10.2 `AGENTS.md` 模板（可直接使用）

```markdown
# AGENTS.md

## 项目
门店经营 + AI 短视频营销 SaaS。详见 docs/开发文档.md 与 docs/architecture.html。

## 技术栈（不得擅自更换）
- 后端: Go 1.25, connect-go, sqlc+pgx, Atlas, Temporal, NATS, Eino ADK
- 前端: React 19 + Vite + TanStack + shadcn/ui + Tailwind v4
- 小程序: Taro 4 (React)；App: Expo (React Native)
- 数据库: PostgreSQL 17 (RLS 多租户) + pgvector, Valkey

## 常用命令
- 启动依赖: docker compose up -d
- 生成代码: make gen   (buf generate + sqlc generate)
- 后端测试: make test-backend
- 前端: pnpm dev --filter admin-web
- 全量检查: make check  (提交前必须通过)

## 工作流程
1. 开发前先读 docs/specs/ 下对应的 Spec，不清楚就提问，不要猜
2. 接口变更先改 proto，再 make gen
3. 数据库变更只能通过 db/migrations，并同步写 db/queries
4. 每个 service 方法都必须有测试；bug 修复必须先写能复现的测试
5. 完成后在 Spec 的"实现记录"里写上变更摘要

## 硬性约束
- 金额一律 int64 分；时间一律 TIMESTAMPTZ / UTC
- 所有查询必须在租户上下文中执行，禁止绕过 RLS
- 禁止跨模块直接访问对方的表，只能调用对方的 service 接口
- 禁止在代码中写死密钥
- LLM 生成的内容里的价格/库存等事实必须来自数据，不能由模型编造
- 不要引入新依赖，除非 Spec 或 ADR 里允许
```

### 10.3 Spec 模板

```markdown
# Spec: M1-库存预警

## 背景与目标
## 用户故事
- 作为店长，当某个 SKU 库存低于预警值时，我希望收到推送，这样能及时补货。
## 业务规则
1. 预警值按 SKU 设置，默认 5
2. 库存变动后实时判断，同一 SKU 24h 内只推送一次
3. 同时发布 stock.low 事件（供 Agent 消费）
## 数据变更
- inventory.warn_qty；新表 stock_alert_log(...)
## 接口（proto）
- InventoryService.SetWarnQty / ListLowStock
## 前端
- 后台：商品列表可批量设置预警值；首页预警卡片
- App：推送 + 预警列表页
## 验收标准（可测试）
- [ ] 库存从 6 降到 5 触发一次推送；再降到 4 不重复推送
- [ ] 其他租户看不到本租户的预警
- [ ] stock.low 事件 payload 符合 schema
## 非功能
- 预警判断不阻塞收银主链路（异步）
## 实现记录（AI 填写）
```

### 10.4 推荐的 AI 协作方式

| 做法 | 说明 |
|---|---|
| **一个 Spec 一个分支一个 PR** | 粒度控制在 AI 一次能完成、人能 30 分钟内审完 |
| **契约先行** | 先让 AI 只改 proto 和迁移文件，人审过再写实现，返工最少 |
| **并行 Agent** | 用 Cursor 的后台 Agent 或 git worktree 让多个 AI 同时开发互不相关的 Spec（例如餐饮包和服装包） |
| **测试是 AI 的"护栏"** | 验收标准写成测试用例，AI 迭代到测试全部通过为止 |
| **MCP 给 AI 装工具** | 给编码助手接入 Postgres MCP（只读，查库结构）、Playwright MCP（自测前端页面）、GitHub MCP（管理 PR） |
| **Bugbot / AI Review** | PR 开 AI 自动审查，但合并前必须人工确认 |
| **定期"对齐"** | 每个里程碑结束后，让 AI 对照本文档检查实现有没有偏离 |

### 10.5 建议的开工顺序（直接丢给 AI 的任务队列）

1. 初始化 Monorepo（pnpm + turbo + Go module + buf + sqlc + Atlas + docker-compose）
2. 实现 `platform`：租户 / 门店 / 员工 / 登录 / RBAC / RLS 中间件

4. `catalog` + `inventory`（通用）→ 服装款色码扩展 → 餐饮菜品扩展
5. `order` + `payment`（先接 Mock 支付，再接真实机构）+ POS 收银页
6. `member` + `report`
7. 餐饮：桌台 + 扫码点餐 + 后厨打印
8. `channel`：代理、报备、佣金、结算
9. `mcp-store` + `ai`（Snapshot → Signal → Agent 流水线）
10. `avatar` + `renderer` + `media`
11. `distribution` + `crm`

## 12. 合规与风险

| 风险 | 说明 | 应对 |
|---|---|---|
| **二清风险** | 平台代收商户货款再结算给商户，属于违规"二次清算" | 聚合收款资金直接进商户自己的账户（持牌机构进件）；平台只收 SaaS 费 |
| **AI 生成内容标识** | 《人工智能生成合成内容标识办法》（2025-09-01 施行）要求显式和隐式标识 | 视频里加"AI 生成"角标 + 文件元数据隐式标识；发布时勾选平台的 AI 声明 |
| **深度合成 / 肖像权 / 声音权** | 克隆他人形象、声音，必须取得本人**单独同意** | 实名 + 活体 + 电子签授权书；只允许克隆本人（或有授权的员工）；支持撤回授权和删除模型 |
| **平台规则** | 抖音对 AI 数字人、批量发布、营销号有限流甚至封号风险 | 控制发布频率、内容差异化（每条脚本都不同）、带真实门店 POI；不承诺流量效果 |
| **视频号能力受限** | 没有全面开放发布 API | 半自动方案；销售话术如实说明 |
| **代理体系** | 多级分佣容易被认定为传销 | 分佣不超过 3 级；佣金只来自真实的 SaaS 销售；不收入门费；律师审核代理协议 |
| **广告法** | 口播里的极限词、虚假宣传 | 审核 Agent + 词库 + 店主确认后才能发布；最终责任归属写进用户协议 |
| **个人信息保护** | 会员手机号、线索信息 | 加密存储（KMS 字段级加密）、脱敏展示、最小权限、导出审计、PIPL 合规 |
| **LLM 幻觉** | 编造价格或库存 | 事实锚定 + 审核核对（见 4.3） |
| **供应商依赖** | 数字人 / 大模型厂商涨价或停服 | 适配器模式 + 至少两家供应商 |

### 14.3 需要向客户确认的问题清单

1. **目标规模**：第一年预计多少商户？高峰期同时在线多少门店？（决定架构投入）
2. **收款模式**：客户有没有现成的支付机构代理关系？商户进件由谁负责？
3. **数字人效果要求**：能接受的单条成本上限是多少？对口型真实度的预期？
4. **视频号**：能否接受"半自动"发布？
5. **代理分佣模型**：直接比例还是级差？几级？个人代理怎么开票、代扣税？
6. **乱价管控力度**：代理能不能自主定价？折扣区间是多少？违规怎么处罚？
7. **硬件**：是否要自带收银硬件一起售卖？指定品牌吗？
8. **行业扩展**：除了餐饮和服装，后续还会加哪些行业（美业、零售、烘焙）？
9. **私有化**：是否有大客户要求私有化部署？
10. **品牌与 UI**：有没有现成的品牌 VI？App 叫什么名字？
11. **上线时间**：有没有硬性时间节点（招商会、展会）？
12. **数据归属**：商户数据、视频、克隆模型的归属和删除政策。
