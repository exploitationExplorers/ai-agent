rag-webfallback.mjs 代码分析报告

该脚本实现了“本地知识库优先 + 不足时联网补充 + 再评估 + 最终生成”的回退式 RAG（Web Fallback）流程。

1) 整体流程（Web Fallback）

START
→
route_question
→
simple?
→
direct_answer
→
END
route_question
→
local_retrieve
→
evaluate_local
→
enough?
→
generate / web_search
→
evaluate_local(二次)
→
generate
→
END

关键点：不是一上来就联网，而是先用本地 Milvus 证据；只有评估不足时才触发 Web 搜索。

2) 核心状态与模块

GraphState 字段

  • retrievedDocs：本地检索结果。
  • localContext：本地文档拼接上下文。
  • webContext：联网补充内容。
  • evaluation：充分性评估（JSON 字符串）。
  • generation：最终回答文本。

结构化输出

  • RouteSchema：simple/complex 路由。
  • EvaluateSchema：enough/missing/reason/web_query。
  • 用 Schema 限制输出，降低流程分支歧义。

外部能力

  • 本地：Milvus + Embeddings 相似度检索。
  • 联网：Bocha Web Search API。
  • 生成：同一 LLM 负责路由、评估、回答。

  • 含义：通过条件边形成“评估-联网-再评估”的决策循环。
  • 特征：能根据证据充分性动态控制是否联网。

4) 优点

本地优先 动态回退联网 结构化评估 可解释引用
  • 相比“固定联网”，先本地后回退更省成本、延迟更低。
  • 评估器机制让联网行为更有依据，而不是拍脑袋。
  • 生成阶段鼓励引用依据，增强可核对性。

5) 缺点 / 风险点

代码正确性风险

  • 当前文件中有 thrownewError、returnJSON.parse 这类写法，若源码一致会导致运行错误。
  • 建议先做语法修复，再做功能验证。

联网结果可信度

  • Web 摘要质量和来源可靠性不稳定，存在噪声与时效偏差。
  • 建议增加来源白名单或可信域名加权。

循环控制风险

  • web_search -> evaluate_local 是循环边，需额外轮次上限防止极端情况下反复兜圈。
  • 建议增加 webRetryCount/maxWebRetries。

性能开销

  • simple 分支也会先初始化 Milvus（main 里提前连接）。
  • 建议延迟初始化：只有进 complex 才连接本地向量库。

配置硬编码

  • question、k、Milvus 地址、web 搜索 count 均写死。
  • 建议支持 CLI 与环境变量，便于复用部署。

评估偏差

  • “enough”由模型判断，可能过于乐观或保守。
  • 建议引入规则校验（是否包含关键实体、是否给出可核对引用）。

6) 建议的优化优先级

  1. 先修复潜在语法问题并补最小回归测试，保证稳定运行。
  2. 增加联网循环上限与失败回退，避免长尾卡住。
  3. 做 Milvus 延迟初始化，优化 simple 路径时延。
  4. 加入来源可信度策略与引用后处理，提高答案可靠性。
