rag-query-router.mjs 代码分析报告

该脚本在基础 RAG 上增加了“问题路由器”：先判断问题简单/复杂，再决定“直答”还是“检索增强生成”。

1) 整体流程（路由版 RAG）

START
→
route_question
→
simple ?
→
direct_answer
→
END
route_question
→
complex ?
→
retrieve
→
rag_generate
→
END

核心价值：把“低成本直答”和“高质量 RAG”做动态分流，减少不必要的向量检索调用。

2) 核心组件说明

LLM + Embeddings

  • llm 用于路由判定、直答、RAG 生成（同一个模型实例）。
  • embeddings 仅用于向量检索路径。
  • 均通过 OPENAI_BASE_URL 和 OPENAI_API_KEY 配置。

结构化路由

  • RouteSchema 限定输出只能是 simple 或 complex。
  • reason 记录路由原因，可用于日志与调试。
  • 比纯自然语言判断更稳定，减少分支歧义。

图状态

  • 在基础字段上新增 strategy、routeReason。
  • 统一在节点间传递，方便最终结果回溯“为何走这个分支”。

Milvus 检索

  • 仅在 complex 分支触发。
  • 输出包含分数和元数据，便于可观测性与结果解释。

4) 优点（当前实现做得好的地方）

结构化路由 分支清晰 流式输出 检索日志可观测
  • 路由层把“是否检索”前置，架构上比固定全量 RAG 更灵活。
  • StateGraph 拆分节点职责，后续可插拔重排、过滤、评估节点。

5) 缺点 / 风险点（你关心的“还有什么问题”）

路由误判风险

  • 复杂问题被判成 simple 时，会跳过检索导致“看似流畅但不准确”。
  • 建议增加置信度字段，低置信时强制走检索或“双路并发后择优”。

不必要初始化开销

  • 即使 simple 直答，也会先连接并加载 Milvus（L208-L238）。
  • 建议延迟初始化：仅在路由结果为 complex 时连接向量库。

配置硬编码

  • question、k、collectionName、url 均写死。
  • 建议改 CLI 参数 + 环境变量，便于复用和部署。

召回质量可提升

  • 当前只有向量相似度检索，无 rerank、无 metadata 过滤。
  • 建议加 BM25/混合检索、重排器、章节过滤与邻域扩展。

鲁棒性不足

  • 缺少启动时配置校验（API key、baseURL、Milvus 可达性）。
  • 缺少超时、重试、熔断与请求级错误分类。

可测试性不足

  • 核心逻辑耦合在脚本中，缺少单元测试与回归测试样例集。
  • 建议把路由、检索、提示词构造、结果后处理拆成可测试函数。

6) 建议的下一步优化优先级

  1. 先做“Milvus 延迟初始化”，立刻降低 simple 问题延迟和资源占用。
  2. 给路由加“置信度 + 回退策略”，降低误判代价。
  3. 参数全部外置（CLI + env），再补一组最小化自动化测试。
